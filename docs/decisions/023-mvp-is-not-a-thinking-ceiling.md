# ADR 023：mvp.md 约束实现，不约束构思

## 背景

主代理被写成产品思考者，但工作流要求每个任务先读 `Agents.md` 再读 `mvp.md`。`mvp.md` 的必做、切片表、「当前限制」和「后续只补本页已写缺口」被当成思考边界。`concept.md` 又写「不因总纲存在而扩大任务」，远期层（视频、配音、音乐、合成、Version）在讨论阶段就被掐掉。

用户纠正产品（例如「Image API 一次出一整页漫画」）之后，代理仍按 `mvp.md` 旧句和 `/goal` 清单收口。用户要求去掉仪式化重读、改提问规则，并怀疑 `mvp.md` 在限制发散。

## 决策

1. **讨论与实现分开。** `concept.md` + 用户当场表达 = 构思材料。`mvp.md` = 写代码 / 派切片时的唯一实现基线。
2. `mvp.md` 的「当前限制」不得用来结束产品讨论。限制只在改仓库时生效。`concept.md` 不得单独当作实现许可，但可以当作构思材料。
3. 主代理先形成产品判断，再决定问不问、派不派。只有真正的产品分叉才提问，一次一个。已说清的指令直接执行。
4. 主代理读当前问题会错的那几处实现；禁止为仪式通读 `Agents.md` 或把整仓实现塞进上下文。
5. 子代理固定 `grok-4.6` + `medium`。主会话保持用户配置的 effort（`xhigh`）。用户覆盖：子代理模型由 4.5 改为 4.6。
6. 不要在很长、刚压缩、或余额不足的会话上开 `/goal`。用户当场纠正后写入 `mvp.md`，不依赖压缩摘要。
7. 撤回 Herdr / Claude：不再启动、等待或假装审查。文案与机械改动走 Grok 子代理或主代理直接改；切片后由主代理审报告。

本决策修正 [ADR 018](./018-baseline-follows-user.md) 的误用：018 的「用户覆盖优先于 concept 远期规格」只约束**实现许可**，不约束**能不能想**。

## 后果

- `Agents.md` 去掉每任务重读和「先问到 90%」；工作流从用户原话和 `concept.md` 起。
- `mvp.md` / `concept.md` 开篇写明：基线不是构思上限。
- 派活前仍须把用户锁定的新范围写入 `mvp.md`，避免未改基线就写代码。
