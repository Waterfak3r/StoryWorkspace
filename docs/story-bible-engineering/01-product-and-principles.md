# 产品边界与核心原则

> 对应原规范第 0–2 章；章节编号与规范关键词保持不变。

## 0. 文档目的

本文定义一个 AI-native 剧本编辑器的核心工程边界。系统在作者写作过程中识别人物、地点、道具、组织、关系、事件等实体，维护可追溯的 Story Bible，并在分镜、生图、视频和配音阶段按 Scene 精确编译生成上下文。

核心目标是实现：

```text
Write once, generate everywhere.
```

同一套结构化事实和素材应服务于续写、剧本、分镜、图像、视频和配音，不要求用户为每个下游模型重复描述角色和世界观。

本文是实现规范，不是 UI 视觉稿、商业计划或模型选型报告。若本文与临时代码实现冲突，以本文中的数据不变量和模块边界为准；修改这些不变量前必须先更新本文和迁移方案。

## 1. 产品目标与非目标

### 1.1 产品目标

系统 MUST：

1. 在编辑器中增量识别 `Character`、`Location`、`Prop`、`Organization`、`Relationship`、`Event` 等实体及其提及位置。
2. 自动创建实体草稿卡，并从作者文本中提出结构化事实补全建议。
3. 严格区分作者明确表达的 `Canon`、模型推断的 `Inferred` 和尚未生效的 `Pending Patch`。
4. 为 Chapter、Scene、Beat、Shot 与实体建立稳定、可查询、可审计的关联。
5. 区分角色永久特征 `Character Base` 与场景/时间点状态 `Character State`。
6. 在视频化时优先按 Scene 的确定性关联装配上下文，仅在需要历史剧情时执行受控检索。
7. 通过模型无关的 `Prompt Compiler` 和 `Provider Adapter` 支持文本、参考图、provider character ID 等不同输入能力。
8. 为每项生成结果保存输入快照、使用的事实版本、模型参数和来源素材，以支持复现与追责。
9. 允许用户接受、拒绝、编辑、撤销 AI 建议；AI 不得绕过该机制直接覆盖 Canon。
10. 支持同一 Story Bible 被写作、分镜、生图、视频和配音模块复用。

### 1.2 非目标

首个版本不以以下能力为目标：

- 完全自动完成一部长片并替代作者的创作判断。
- 在没有用户确认或明确策略授权的情况下，把 AI 推断写成正式设定。
- 用向量检索替代实体关系、场景关联、状态解析或事务数据库。
- 为所有视频模型提供完全相同的视觉一致性保证。
- 首期实现多人实时协作、复杂权限系统、全自动版权清理或资产训练平台。
- 首期构建通用知识图谱查询语言。
- 让下游 Provider 直接读取数据库或修改 Story Bible。
- 通过超长 Prompt 无差别注入整个项目内容。

## 2. 核心设计原则

### 2.1 文本是证据，结构化数据是可审计投影

剧本文本是作者表达的原始证据。Story Bible 是从文本和用户操作得到的结构化投影。所有结构化事实 MUST 保留来源，至少包含：

- 来源文档、Scene 和文本范围；
- 创建方式：用户输入、规则抽取、模型抽取、导入；
- 创建者或模型运行 ID；
- 创建时间和版本。

删除或改写文本不得无痕改写 Story Bible。系统应生成失效、冲突或重验证 Patch。

### 2.2 AI 建议，不静默改 Canon

LLM 输出 MUST 先通过 schema 校验并转为 `Pending Patch`。除纯机械且可逆的操作外，模型不得直接执行数据库写入。

允许自动执行的机械操作包括：

- 记录文本 mention；
- 通过已确认别名做精确实体链接；
- 创建无事实内容的 entity draft/stub；
- 更新搜索索引；
- 标记旧提取结果需要重算。

事实新增、覆盖、合并、关系变更和冲突解决默认 MUST 经过 Patch。

### 2.3 Canon 与 Inferred 永不混存

`Canon` 与 `Inferred` 必须有独立的记录类型或明确字段，查询时不可默认合并为单一“真相”。下游生成默认只使用 Canon；只有调用方明确允许时才可使用 Inferred，并应带置信度阈值和显式标签。

### 2.4 先确定性装配，再语义检索

当前 Scene 已关联的实体、状态、素材和约束必须通过关系表直接读取。RAG 只用于补充开放式历史剧情、主题或相似情节，不得作为主数据查询层。

### 2.5 Base、State、Event 分层

- `Base`：长期稳定或身份级信息。
- `State`：在某个 Scene 或时间区间内成立的可变信息。
- `Event`：导致世界状态发生变化的叙事事实。

系统不得用覆盖 Base 的方式表达换装、受伤、持有物、情绪或位置变化。

### 2.6 Stable ID 优先于名称

名称、昵称和语言都可变化。内部关联必须使用不可变 UUID。Scene 重排不得改变 Scene ID；实体改名不得破坏历史链接。

### 2.7 Provider 能力不泄漏进领域模型

Story Bible 保存 provider-neutral 的事实和资产。特定模型的 character ID、LoRA、reference token、参数限制必须保存在 Provider Binding/Adapter 层，不得写入角色基础字段。

### 2.8 每次生成必须可复现

每个 Shot/媒体生成任务 MUST 保存不可变的 `Generation Manifest`，包含编译前上下文、编译后请求、事实版本、资产版本、Provider、模型、参数、seed（如支持）和结果。

### 2.9 增量、异步、可降级

编辑输入不得等待 LLM。文本保存和解析任务解耦；识别失败不得阻塞写作。系统应能退化为普通剧本编辑器，并在后台重试抽取任务。
